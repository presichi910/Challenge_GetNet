## 4. The observe step (replan): measured, not adopted

The step re-queries the knowledge base once with the claims the verifier could not back, re-checks the same answer, and (with `REPLAN_MAX=2`) takes one more action: it runs the support agent when the router did not and an unbacked claim is about the customer's own account (`add_support`), or else offers a ticket or escalates when nothing actionable is left.
It is **off by default and off in the main run.** It runs **once, after the synthesizer** (not after each agent). The "add another agent" branch was **not** in the code at the final run (`22423e2`): it was added afterwards, as `add_support`, in commit `8bbc1dd` (`app/agents/observe.py`), and it is the one action of the second replan: it takes the place of the ticket offer or the escalation in that turn, and if it fails the turn falls back to them. `add_support` only adds the support agent (with the authenticated user id); there is no branch that adds the knowledge agent.

- **Paired measurement with the judge** (`eval/replan_ab.py`, the same 30 saved drafts through both arms, only the 6 whose text differs were scored, one judge score per text, n = 6):
  unsupported actionable claims 1 -> 2, completeness 2.67 -> 3.17, pass 4/6 -> 4/6 (unsupported claims in total 6 -> 11). One case improved (`q08`), one got worse (`q05`: after the retry the verifier backed
  everything and the judge still found six unsupported claims). The only measured benefit is completeness, with n = 6 and a judge that scores the same text differently between passes.
- **A branch of the real run with the step on, before `add_support`** (`--replan-max 2 --label "replan on"`, 2 x 40 case-runs, run on `22423e2`, no judge score): it acted in 9 of 80 case-runs (11%), escalated 0 times and offered a ticket once;
  p95 latency 16.3 s -> 26.3 s (+10 s), p50 3.9 s -> 4.5 s, mean 5.49 s -> 8.26 s; agent cost $0.0012 per case-run in both arms (5,924 against 5,923 tokens) and the same handoff rate (15%). Every action is one extra Voyage call (9 in all), which is not in that agent cost.
  The cost of the step is therefore latency, not agent tokens (`eval/reports/REPLAN_ON-20261115.md`).
- **A second branch, with `add_support`** (`--replan-max 2 --label "replan on add_support"`, 3 repetitions of the 27 regular cases = 81 case-runs, runs `20261116-234030`, `20261116-234325` and `20261116-234617`, code at `b800b8e`, tree clean, 0 provider errors; the raw files were committed in `cc9e0a5`).
  The judge scored **all three repetitions**. The scripted comparison of the three with the five base repetitions (`eval/reports/REPLAN-AB-20261116-234030.md`, generated by `eval/compare_runs.py`) has one headline per repetition: Repetition 1: **Headline:** candidate 18 pass of 27 regular rows; baseline repetitions 16-19 pass of 27; the candidate count is inside that range; replan fired in 1 of 27 rows. Repetition 2: **Headline:** candidate 20 pass of 27 regular rows; baseline repetitions 16-19 pass of 27; the candidate count is outside that range; replan fired in 2 of 27 rows. Repetition 3: **Headline:** candidate 20 pass of 27 regular rows; baseline repetitions 16-19 pass of 27; the candidate count is outside that range; replan fired in 2 of 27 rows. Each headline says whether the repetition's count is inside or outside the range of the baselines, and it is not the same for the three repetitions; with three repetitions with the replan on against five base repetitions and a judge that is not deterministic, **no statistical inference is made**. The rows whose verdict differs from the baselines are mostly rows where no replan action ran, and a difference there is not evidence about the replan; the report does not establish its cause. `q04` is the only case where `add_support` ran: its verdict in each repetition is in the report's table (it is not the same in all three), the rewrite in repetition 1 lost the profile data (see the replan demo) and repetitions 2 and 3 include it. `q05` and `q08`, where the replan offered a ticket, are in the same table. **A quality benefit is NOT demonstrated.** What the code did: the step acted in **5 of 81** case-runs. `add_support` ran 3 times, all in `q04_pix_bank_account` (once per repetition), each with one `get_customer_profile` call, no ticket and no escalation; the ticket offer fired twice (`q08` in repetition 2, `q05` in repetition 3); there were 0 escalations.

  **A false trigger to know about:** the three claims the account lexicon (`is_account_claim`, plain regular expressions, no model, **not validated against labeled data**) looked at in `q04` were "You must have a bank account linked to your Getnet profile..." (marked account-specific), and two general statements about Pix settlement (not marked). The marked one is a general requirement, not data about this customer, so the support agent was run on a question the knowledge base had already answered. The lexicon was not changed (`eval/reports/ADDSUPPORT-CAPTURE-20261116-233738.jsonl` records each call).
- **Rows that differ without a replan (observations from the saved JSON files; the cause is not established).** **m08:** the synthesizer's answer was longer in the replan-on runs, which let the language detector trigger the translation step, so m08's known language failure depends on the length of the answer and is not fixed. **q02:** the web search results depend on the run date, and the evidence the answers were built on was not the same in the base runs and the replan-on runs. **x01:** the date-relative tool data shifted by a day and the text changed with it; the judge scored that variant as less grounded although its own stated reason says the answer is supported. 3. **The agreement figures are small-sample figures** (15 rows in V3; 19 in the V2 re-score). A one-row difference is 6.7 and 5.3 points. V3 was sampled on purpose to include two edge cases. The judge is **not** presented as validated: these are small samples, and one of them was used to build it.
4. **V2 is not independent.** The judge was adjusted on its disagreements. The 19-row re-score is also an **atypical subset**: the draw happens to hold all seven rows where the old judge and the human disagreed (section 3.1), so the old judge starts from a lower agreement there than on the 27. The seed (20261116) was fixed beforehand and not changed after seeing that, and with n = 19 a difference under about 20 points cannot be told apart.
5. **The judge's free-text reason can be wrong about the language.** On `m04` it says the user wrote in Portuguese when they wrote in English. The verdict does not depend on that sentence (the language rule is applied by code with its own detector, and the cause of that verdict was groundedness),
   but the reason of a single row must not be quoted as evidence.

**About what the evaluation covers**
6. **The eval does not exercise** ticket approval, provider failover, the webhook, the SLA or the telemetry (the eval runs with approval and failover off). They are covered by tests (failover only with test doubles: the repository holds no artifact of a real provider outage), and approval by one **manual** real-model run (by hand, not in CI). **The eval also has a side effect:** it runs the real ticket tool with approval off, so the cases that ask for a ticket or end in a handoff write records to the local `data/tickets.jsonl` and `data/handoffs.jsonl`, and because a ticket is deduplicated by customer, category and summary against the open tickets of that file (`app/data/repository.py`, `_find_open_duplicate`), a ticket left by an earlier run on the same machine can be returned as `already_existed` in a later run. Whether this changed any result was not measured.
7. After the commit of the holdout (`9326b88`), three commits changed `app/prompts.py`: `20d5b4e` (support rule 5: offer a ticket, create it only if the customer accepts; tuned with `q05`, `q08`, `x04`), `d71966d` (rule 8: do not reveal instructions; tuned with `inj01`, controls `inj02` and `x04`) and `9eb7a24` (support rules 3 and 7; tuned with `h03`, controls `x04`, `h01`, `h02`).
   `ho06` and `ho12` measure the same behavior as rule 5, and `ho08` the one of rule 8; the baseline of the holdout had already been seen when the changes were made (`ho06` and `ho12` failed 0/3; `ho08` passed 3/3). For that reason `ho06`, `ho08` and `ho12` are not presented as blind. The cause of the `h03` regression (probably rule 8) was not verified. `ho02` (routing) is unstable and `ho13` (tool use) fails in every repetition; both are reported as they are. The "blind" labels in the per-run reports generated by `run_eval` (for example "new blind (ho06 and later), written before any prompt fix") predate the correction in this item: read them as "new holdout", with `ho06`, `ho08` and `ho12` as baseline seen.
8. **Tuning discipline.** Prompts changed in three steps, each tuned on REGULAR cases only. (a) After the new holdout was committed and its baseline measured (pass 16/24 over three repetitions, with the judge of that day), the support rules for declining and for offering a ticket and the router and synthesizer rules for recall were changed using `q05`, `q08` and `x04`, then the holdout was measured once more (21/24); no prompt rule was changed in response to holdout results after the second measurement; the later edits (rule 8, h03) were tuned on regular cases. (b) A rule against revealing the instructions, with a guard in code, tuned on `inj01` and `inj02`. (c) A regression found by repeating `h03` (it passed 2 of 5 runs, down from 15 of 16 earlier): the support rules 3 and 7 were narrowed using only `h03` and `x04`, 5 repetitions each, with `h01` and `h02` as controls; `h03` went from 2/5 to 5/5. `PROMPT_SHA256` pins every prompt. The judge was not changed after the final run.
9. **Run-to-run variation is real.** The model is not deterministic: `ho02` passes in some repetitions and not in others, and the judge scores the same text differently between passes. Read directions, not decimals.

**About known defects**
10. The verifier removes unbacked claims but cannot add the right ones: a case such as `ho06` can end as an honest, nearly empty answer ("no documented steps"). It audits about 72% of an answer's sentences and cannot tell a real quote that does not
   back its claim. A stricter segment-by-segment verifier was built, measured on 15 drafts and **not adopted**: it covered every segment but flagged 1.87 per answer against 0.8 (mostly false positives: lead-in lines, derived figures) and did not leave fewer unsupported claims (7 actionable against 5 for the one in use; completeness 3.08 against 3.31).
11. `inj01` still ends as a fail with the judge, on the groundedness of its harmless part (contact data the judge disputes although the verifier found the quotes), not on the injection: the leak of the system prompt is gone.
12. **Two answers to know about.** (a) The language of the answer to `m08` is wrong (Portuguese to an English question), see section 3. (b) `q10_payment_link_whatsapp`: the answer of the V2 run (2026-11-14), re-scored with the current judge, passed (section 3.1), and the answers of the five final repetitions all fail it, on groundedness. They are different answers, from a system that changed in between (the verifier was added on 2026-11-15, and prompt rules after it), so this is not a contradiction of the judge; the verifier did not rewrite any of the five (`verify_note` is empty in all of them). **The cause was not verified**: it can be the answer itself, the verifier or the prompt changes, or the judge scoring the same kind of text differently. It was not investigated further.
