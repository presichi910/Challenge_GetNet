# Spec: Getnet Multi-Agent Support System

Written before implementation (Spec-Driven Development). Each requirement has an acceptance check that is either an automated test or an evaluation case.

## 1. Goal
HTTP service that answers Getnet customer messages by orchestrating specialised agents, grounded in Getnet's website and in the caller's account data, packaged with Docker.

## 4. Orchestration contract

State (`app/state.py`): persistent fields `messages` (reducer `add_messages`), `user_id` (from the token, never from the model), `conversation_id` and `summary`; per-turn fields `plan`, `step`, `language`, `agent_outputs`, `final_answer`, `wants_human`, `handoff`, `verify_note`, `observe` (what the observe step did) and `approvals` (ticket requests sent for approval), which the router resets every turn.

Graph: `START -> [summarize ->] router -> {support|knowledge}* -> (synthesizer | handoff)`, and after the synthesizer `-> observe -> verify -> [request_approval ->] END`; `handoff -> END`. The next node is `plan[step]`; when the plan is exhausted it is `handoff` if `handoff_reason(state)` is set, otherwise `synthesizer`. If `wants_human` is set, the router goes straight to `handoff`. `observe` goes to `handoff` instead of `verify` when it sets `escalate`. `request_approval` is a node only when approvals are configured, and runs only when the turn proposed a ticket. The nodes `summarize`, `observe`, `verify` and `request_approval` are passed in to `build_graph`; without them the graph is the plain `router -> agents -> synthesizer` one.

Handoff triggers (`handoff_reason`, a pure function of the state):
- `user_requested`: the router set `wants_human` (explicit request, any language).
- `technical_failure`: every agent in the plan failed (no answer or error).
- `agent_unresolved`: every agent that answered called `escalate_to_human`; also when one of them did and the turn proposed a ticket (the escalation wins over the proposal, and the handoff opens its own ticket); also when the observe step finds nothing in the answer backed (`REPLAN_MAX>=2`), or when the support agent it adds cannot resolve the case.
- `approval_expired` (opened by the approval sweep, not by `handoff_reason`): a ticket request nobody decided in `APPROVAL_TTL_MINUTES`.
- Otherwise none. A retrieval-relevance threshold was rejected: measured scores of answerable (0.41-0.67) and unanswerable (0.37-0.50) questions overlap.

Routing rules:
- Account-specific (deposits, terminal, declines, transactions) -> `support`.
- Product/how-to/general-purpose -> `knowledge` (which decides RAG vs web search).
- Both needed -> `support` first, then `knowledge`.
- Greeting/unclear/out-of-scope -> empty plan, synthesizer answers directly.
- Router failure -> `["knowledge"]`.

Synthesizer: 0 outputs -> direct reply; 1 -> passthrough; 2+ -> merge; all failed -> static fallback.

Observe and verify (after the synthesizer; `app/agents/observe.py`, `app/agents/verifier.py`). Decisions are made by code; the model only audits and rewrites.
- `verify` lists the answer's claims, the code checks each quote against the evidence, one rewrite deletes the claims without support, one translation fixes the answer's language, and a guard replaces an answer that repeats 10 or more consecutive words of a system prompt. It fails open.
- `observe` does nothing with `REPLAN_MAX=0` (the default): the graph and the state are those of the graph without it.
- `REPLAN_MAX>=1`, replan 1 `retry_kb`: one knowledge-base search with the unsupported claims grouped, the same answer audited again against the old evidence plus the new passages, and only what is still unsupported deleted.
- `REPLAN_MAX>=2` (a larger value behaves like 2), replan 2 is ONE action, the first that applies: `add_support` (the router did not send the support agent, there is a customer, and a claim still unsupported is about that customer's account: the support agent runs with the authenticated user id, the answers are merged and the merge is audited again); otherwise a ticket offer (the answer had steps and none is left), or an escalation (nothing in the answer is backed). If `add_support` fails, the turn falls back to the ticket offer or the escalation.
- It acts only on a turn that used Getnet's knowledge base or the support agent, uses no retrieval-score threshold (only counts of claims) and records everything in `routing.replans` of the response. There is no action that adds the knowledge agent, and `observe` runs once after the synthesizer, not after each agent.

## 5. Out of scope (for now)
Guardrail classifiers (only a prompt-leak guard exists), alert delivery (Alertmanager) and a Langfuse export, a real customer backend, an operator UI, a production identity provider and refresh-token handling (the Keycloak in compose is a development setup), reassigning a claimed case to a named operator, a push to the customer (operator replies and approval results arrive on the next `/chat`), a shared rate-limit store and more than one worker, and encryption of `handoffs.sqlite`. Metrics, OTLP traces, a Grafana dashboard, RS256 tokens checked against a JWKS with a revocation list, a rate limit per caller and a signed webhook to the operators exist; see the README.

## 6. Design decisions
- Routing style: multi-step plan (chosen) vs single-agent vs supervisor loop.
- Customer data: mock JSON in-process (chosen).
- Memory: LangGraph checkpoints in SQLite (`SqliteSaver`, `CHECKPOINT_DB_PATH`), `thread_id = "<user_id>:<conversation_id>"` with `user_id` taken from the JWT (chosen). Rolling summary above `SUMMARY_THRESHOLD` messages, only the latest checkpoint per thread kept, TTL of idle threads (`THREAD_TTL_DAYS`) and a limit of conversations per customer (`MAX_THREADS_PER_USER`, HTTP 429). The eval and tests that pass no checkpointer still use `MemorySaver`. See README, "Conversation memory".
- Models: one variable per role (`LLM_MODEL` knowledge, `LIGHT_MODEL` router/support/synthesizer, `JUDGE_MODEL`), passed to the containers by docker-compose (chosen). Support has its own `SUPPORT_MODEL` (default `LIGHT_MODEL`, set to `openai/gpt-oss-120b` in `.env.example`) because the 20b skips `get_recent_transactions` on declines (`q08`); a model change was chosen over a prompt change because the 20b is very sensitive to prompt wording.
- Identity: JWT RS256 only, checked against the identity provider's JWKS (Keycloak in compose, two realms: merchants and operators), `kid` required, no shared secret in the app (chosen; the first demo used HS256 with a shared secret, which was replaced); the id comes only from `sub`. Body `user_id` kept optional for compatibility with the original contract.
- Evaluation: offline dataset + LLM judge (chosen).
- Handoff action: ticket + SQLite operator queue behind a pluggable notifier (chosen); operators work through `/operator/*` (claim, reply approve or reject), and the answer is delivered in the customer's next `/chat` turn. A signed webhook (`WEBHOOK_URL`, `app/webhook.py`) tells the operators about a new handoff, a ticket request waiting for approval and a handoff past its SLA; it is off when the URL is empty, carries no customer text, and does not track the receiver's acknowledgement. See README, "Human oversight".
- Operator reply delivery: stored in SQLite, returned as `operator_messages` on the customer's next turn, and added to the agents' context on that turn as an assistant-side message labelled `[Operador humano] (approve|reject) <text>`, through the ordinary message history (chosen). No prompt, node or router changed; with no reply the input is identical to before. The label is the trust marker, so a customer's own `[Operador humano]` is turned into a quote. With the real LLM the text reaches the agents' context, but they do not reliably use it to answer "what did support say?" (see the README, Limitations).
- Claims: a lease (`HANDOFF_LEASE_MINUTES`, 15) instead of a permanent claim, swept lazily on access, no background job (chosen). `reject` releases (default) or closes without a customer message.
- Privacy of handoffs: erased with their conversation and by the same TTL; the JSONL audit file is redacted (chosen over keeping excerpts there). Importing the old file is opt-in (`HANDOFF_IMPORT_JSONL`).
- Roles: a `role` claim (`merchant` default, `operator`) on top of the scopes; each endpoint family needs its own role (chosen).
- Handoff triggers: explicit user request, technical failure, agent-reported low confidence (chosen); user frustration detection left out as too subjective to evaluate.
